# 0018: CSRF protection with an Origin check + JSON-only bodies

**Context.** Cookies are sent automatically. A page on `evil.com` could submit a hidden form to `our-site/bff/me` and your browser would attach your login cookie. That's **CSRF** (cross-site request forgery).

**Decision.** Three layers, all in `web/lib/server/`:
1. `SameSite=Lax` cookies: browsers don't attach them to cross-site POSTs at all.
2. **Origin check**: every POST to `/bff/*` must carry `Origin` equal to our own site. Browsers add this header and pages can't fake it.
3. **JSON only**: `content-type` must be `application/json`. An HTML form can't send that, and a cross-site `fetch` with JSON needs a CORS preflight, which we never answer.

Every BFF POST goes through `bffPost()`, so a new route can't forget the check.

**Why not the others.**
- *Synchronizer token (a random CSRF token in a hidden field + cookie)*: the classic approach, still right for apps that use plain HTML forms. It means extra state on every form, which we don't need with JSON + Origin.
- *Next.js Server Actions*: they check Origin vs Host themselves. We chose explicit route handlers because a BFF with named endpoints is easier to learn from, test with curl, and reuse in step 4 (the WebSocket ticket).
- *SameSite alone*: older browsers and some edge cases (top-level GETs, sibling subdomains) don't fully cover it. Defense in depth costs us 15 lines.

**Consequences.** `GET` must never change anything (the refresh route only renews *your own* session, so it's safe). Behind CloudFront (step 10) the origin check must read `x-forwarded-host`, which `siteOrigins()` already does.
